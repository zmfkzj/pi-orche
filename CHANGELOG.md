# Changelog

## [Unreleased]

- **One-shot `/orche strong <PROMPT>` and `/orche ultra <PROMPT>`** (`docs/orchestrator.md` 14.5, `docs/pi-package.md`). The prompt is passed verbatim (lines, quotes, slashes); without a prompt the command shows its own usage and starts nothing. The request is its own run in its mode (prompt section, tools, guard, `orche_task` dispatch via `oneShot`; background jobs keep it until they end). Follow-ups queued during it and results of unrelated earlier jobs are held back and run afterwards, each as its own run in the session's mode; the interrupted-job notice waits for the next ordinary prompt; an unattributable message arriving after main answers (a peer note) ends the request's mode there. Every model request gets the delegation prompt section of the mode in force (`context_with_system` patch). Later turns keep the mode only for a provable continuation: the task with `single.ledger` (persisted on the ledger hand-off, `requestMode`); a reused or handed-over worker without ledgers runs in the session's mode. The session's mode, its saved `/orche mode` entry and the config are unchanged; results add a `Request mode:` line and `details.requestMode` (run.json `assignment.requestMode`, job start entries). **Changed:** `/orche single|strong|ultra|direct <PROMPT>` while main is busy is now refused in every session mode (previously queued as an ordinary follow-up when the session was in the same mode, which lost the explicit mode); a plain follow-up still queues. Help text and completion descriptions describe the one-shot behaviour.

- **ultra integrity and isolation hardening** (`docs/orchestrator.md` 14.3-14.4). Content fingerprints (manifests of raw bytes and modes of every in-scope file; index flags, clean filters and end-of-line rules cannot hide a change) taken before and after every bash call of the ultra orchestrator (probes opened at the tool guard, which now receives the tool call id, and closed at the awaited `tool_execution_end`): a check that overlapped another call that can change files, changed files itself, or was followed by any change (tool, shell command, other process) no longer counts. `orche_adopt` recomputes the candidate's changes and basis tampering, requires a successful check that saw the copy exactly as it is, and verifies the written files (rollback otherwise); the report gate binds selection evidence to the adopted content and integration evidence to the workspace's fingerprint at the report call, refuses a report sent together with other calls, and refuses (never skips) when a fingerprint cannot be taken. Dependency directories (`node_modules`, `.venv`, `venv`) are private copies per candidate (copy-on-write where available), never links to the workspace's own; links into the workspace are re-pointed into the copy, Python environment paths rewritten; every link of a copy is verified through its chain and the copy is refused before any candidate runs when one leads to a writable or unverifiable place outside (a writable outside file in a dependency directory becomes a private copy). Each candidates round is checked for escapes (the workspace's content or its own dependency directories changed: the round's candidates are not adoptable). Submodule paths are blocked for candidates' file tools and named in the result; completed runs free the copies.
- **`strong` and `ultra` modes; strong model tiers** (`docs/orchestrator.md` 14, `src/orchestrator/ultra.ts`, `src/orchestrator/candidate-workspace.ts`). `mainMode`, `/orche mode` and one-turn `/orche <mode> <PROMPT>` accept `strong` and `ultra` (default unchanged: `single`). `models.strong-orchestrator`/`models.strong-worker` (camelCase `strongOrchestrator`/`strongWorker` accepted, both spellings at once is an error): strong and ultra workers run on them; an unset or unresolvable strong orchestrator falls back to `models.orchestrator`, then main (with a warning naming the tier); an unset strong worker inherits the effective strong orchestrator, never `models.worker`. strong is otherwise the single workflow unchanged. ultra adds `orche_spawn` reasons `exploration`/`candidates` (no `parallelism`; `isolation` for specialists only), candidate workspace copies, a protected verification basis, the `orche_adopt` tool (conflict refusal, rollback) and an ultra report gate checked against the tool-call ledger and the runtime stage records; caps: exploration 2, candidates 2 rounds, 4 workers per call, verification rounds unchanged. Reusing a worker across single/strong switches its model with a note; crossing the ultra boundary replaces it with a fresh worker briefed from its transcript. `details.mode`, `details.modelTier`, `details.ultra`, run.json `assignment.mode`/`outcome.ultra`, `/orche models` strong lines.

### Added

- **Long-task timeouts: linear extensions, observation, resume** (README "Activity-aware timeouts", "Observation", "After a timeout"). Extension *n* of an `orche_task` assignment is now `extensionMs + (n − 1) × extensionStepMs` (new key; defaults 10 min + 10 min: 10, 20, … 100 minutes, a 30 min + 550 min = **9 h 40 min** ceiling instead of 5 h 30 min). A config that sets `extensionMs` without `extensionStepMs` keeps its fixed meaning. A new observer (`limits.observeMs`, default 5 min) samples liveness and recorded progress at that period whatever the extension length (progress line `⏱ check …`, `observation` events, `details.observations`); missing progress never stops a worker, but two consecutive checks without any sign of life during an extension end it (`stalled`). Liveness now counts the session events of `orche_spawn` sub-workers and a compaction in flight for up to 15 minutes. A timeout is no longer handled like an unmet result: it neither counts towards nor resets the 2-consecutive-unmet streak, the delegation rule says to continue with the same worker and task, and the failed result carries `Checkpoint at the timeout …` and `Resume: …` lines plus `details.resume` (worker, task, retained-until, checkpoint). With `single.ledger`, every accepted `task_plan` is persisted at once as a `plan` ledger event (the resume checkpoint), restored after reloads, given to the same worker (`## Resuming task … after a timeout`) or to a new worker in its `## Continuing task` briefing, and summarized for main.
- **`orche_spawn` sub-workers get the activity-aware deadline too** (README "`orche_spawn` sub-workers get the same deadline"). Instead of a fixed `assignmentMs` timer, each sub-worker runs `ExtendableDeadline`/`waitExtendable` on the orchestrator assignment's resolved limits (same linear or fixed schedule, `maxExtensions`, activity window, `observeMs`), from its own start and on its own session's liveness. Its timeout reason (idle, budget, stalled) is in its error, a `Deadline:` line of the orche_spawn result, `details.spawned[].deadline` and the `spawn` record event; extensions and checks show in the status lines without counting as the orchestrator's activity. The orchestrator assignment's end cancels its sub-workers at once (timeout included). The advisor keeps its fixed cap.
- **Plan advisor for worker runs** (`"single": { "advisor": true }`, default off; `models.advisor`; `src/single/advisor.ts`, `docs/orchestrator.md` 13). Each standard single-workflow `orche_task` assignment (explore, answer, implement, verify; not specialists, direct mode or `orche_spawn` sub-workers) gets one fresh read-only advisor at the worker's first accepted `task_plan` (or first edit; none if it reports without either), on `models.advisor` with the same tier syntax and inheritance as `models.worker` (unset: the worker's model and thinking). Its advice is steered once into the running worker as advisory notes that grant nothing. No result leaves advice unprocessed (bounded finalization): the worker's first `report_result` switches the advisor off for the rest of the assignment and waits for a running one; a report without `data.advice: {decision: applied|rejected|partial, reason}` for notes it has seen, or written before it saw them, is held and the same session processes them in the same assignment (at most 2 holds, then the assignment fails `advice_unprocessed`); only the final report is returned, once. Advisor failure/timeout leaves nothing to process and never fails the worker; failed/cancelled assignments and shutdown stop it and report existing advice `unprocessed`. `AgentManager.injected(agentId)`. `/orche models` shows the advisor's state and model; results, `details.advisor`, `run.json` (agent `W1.advisor`, `advisor` events) record it. Off means no extra request or delay. `AgentManager.steer` takes an optional `source`/framing; `InjectedMessage.source`.
- **Background `orche_task`** (README "Background tasks"): in TUI/RPC sessions the call returns `Started job J1: worker W1 …` once the worker has its assignment; the result arrives once as an `orche-task-result` message that triggers main's next turn. New tools `orche_task_status {job?, cancel?}` and `orche_task_message {job?, message}` (steer into the running worker; undelivered messages are withdrawn and listed). `wait: true`, print and JSON modes block as before. One job at a time; `orche-job` entries persist starts and ends.
- **Attach/detach for background `orche_task`** (README "Background tasks"): in TUI/RPC the call now stays attached to its job and returns the result like a blocking call; steered user input (queued follow-ups wait for the result, see Changed), a woken pi-session-bus note (`session-bus:message` event), Esc or the new `/orche detach` detach it while the worker keeps running, and main re-attaches with the new `orche_task_attach {job?}` after answering (system-prompt rule; refused while a steer or an undelivered note waits). Results are delivered exactly once (attached call or `orche-task-result` message, with a notification). New `orche-job` widget (running attached/detached with elapsed time, then ✓/✗/⊘/! and where the result went), detached tool blocks no longer show `took Ns`, and a renderer for the result message. `wait: false` starts detached; `wait: true`, print and JSON modes keep the non-detachable blocking call (abort cancels).
- **Worker lifecycle**: worker/job ids are never reused across reloads; naming a gone worker (idle expiry, eviction, stop, reload, crash) hands over to a new worker with the old transcript/record/summary; shutdown marks running jobs and `run.json` records `interrupted`; orphan `running` records of dead processes (`owner.pid`) are closed at session start.
- **Write scope outside the workspace**: private per-worker scratch dir, `writeRoots` (config or per assignment), and a best-effort static check of worker bash write targets with the same policy (not a sandbox).
- **Output-limit recovery** (`src/pi/length-recovery.ts`, docs/length-recovery.md): thinking-only and cut-off length stops without context pressure no longer compact; at most two next-step continuations (the second one thinking a level lower), one forced report, then an explicit `Output limit` failure. Real overflows keep Pi's compact-and-retry. Chosen by a controlled faux-provider benchmark (`experiments/length-recovery/`, results in `results/length-recovery/`; not a real-model measurement) after a survey of other agents; baselines `P3_plain_continue` and `P4_identical_resend` (the Codex/Gemini re-send pattern).
- **Quiet waits**: a bash call with an explicit `timeout` keeps the worker active for deadline extensions within that timeout; the extension budget still caps the assignment.
- **Verification cap**: an orchestrator gets at most two `verification` spawns per assignment (`orche_task` `verificationRounds`, 1–5, raises it when the user explicitly asks for more review); after a refused round the report must carry `data.unresolved` and the result adds a `Verification cap:` line.
- **Schema friction**: TypeBox 1.x error paths, `report_result` `data` sent as a JSON string, unknown tool names answered with a suggestion (never re-routed), task_plan title truncation and clearer requirement-id errors, integer-string arguments, clearer stale-anchor messages, diagnostics fall back to the bundled TypeScript when the project's is incomplete.

- **`orche_task` shows the model and thinking (reasoning effort) its worker runs on** (`src/orchestration/model-use.ts`): the live status line (`W1 implement · <provider/id> · thinking <level> · <n> requests · last tool: …`), each sub-worker's progress line once its session exists, a `Model: <provider/id> · thinking <level>` line below the result header (after its model warnings), the `Sub-workers:` line, the orchestrator's `orche_spawn` report and `/orche workers`. The values are the session's after Pi's clamp, not the configuration's; models that answered this assignment are counted in the new `details.models` / `run.json` `outcome.models` and listed when they are several or differ from the session's; unknown values read `model unknown` / `thinking unknown`, and a sub-worker whose session never started (`notStarted`) is shown as unknown instead of its route. A failed task's error text is unchanged: the TUI draws its `Model:` line from the details. Sub-workers now record their session's model instead of the route's.
- **`"thinking": "main"` in `models.orchestrator` and `models.worker`** (`docs/orchestrator.md` 12): a tier keeps its own model and takes main's current thinking at each hand-off (orchestrator) or spawn (worker), so main's `/thinking` and cycle keys set the effort of other models; in `models.worker` it is main's thinking rather than the orchestrator's. Pi clamps a level the model lacks, and the level actually used is recorded: sub-workers now record their session's thinking after the clamp instead of the requested one. `{ "model": "main", "thinking": "main" }` parses as `{ "model": "main" }`; `"thinking": "main"` in `routes`, `default` and `models.main` is a config error. New `thinkingSource` (`config`, `config:main`, `main`/`orchestrator`, `route`) next to `modelSource` in details, `run.json` and the split log (which also gains `thinking`, and `thinking`/`thinkingSource` per `workerModels` entry). `/orche models` shows a tier's `with main's thinking (<level>)` and a line naming the tiers main's current thinking reaches. Main's hand-off rule now names main's CURRENT thinking only where it is inherited: `{ "model": "main", "thinking": "<level>" }` no longer reads "inherit main's CURRENT model and thinking", and an orchestrator model of its own says whether its thinking is main's or configured. Omitted `thinking` keeps its meaning.
- **`{ "model": "main" }` in `models.orchestrator` and `models.worker`** (`docs/orchestrator.md` 12): names main inheritance explicitly. The tier runs on main's current model and, unless it sets `thinking`, main's current thinking at each hand-off, as before; `{ "model": "main", "thinking": "medium" }` keeps main's model with another thinking level. In `models.worker` it means main's model rather than the orchestrator's. `main` is a reserved value of `model`, which otherwise must be `provider/id`, so it cannot be mistaken for a model id and no earlier valid config changes meaning. `"main"` in `models.main`, a bare string such as `"orchestrator": "main"`, `extendedContext` next to `"main"`, and `"main"` in `routes` or `default` are config errors. `modelSource` gains `config:main` (details, `run.json`, split log), `/orche models` shows `config models.<tier> "main"`, and main's hand-off rule keeps its earlier sentence for `"main"`. Unset tiers behave as before.

- **Model tiers** (`models` in `orche.config.json`; `docs/orchestrator.md` 12): `main`, `orchestrator` and `worker` can each get their own model with the fields of a route (`model`, `thinking`, `extendedContext`), validated like routes. `models.main` is applied to the Pi session with `pi.setModel`/`pi.setThinkingLevel` (current session only) at a fresh start (`startup`, `/new`) without messages or command-line model flags; resumed, forked and reloaded sessions and models picked during the session are kept. `models.orchestrator` replaces main's model for the single workflow's standard roles; `models.worker` replaces the orchestrator's model for its orche_spawn sub-workers (the fresh verifier included). Unset tiers inherit as before, so configs without `models` behave as earlier; game-asset/video keep their routes; an orchestrator or worker model orche's runtime cannot resolve warns and falls back to inheritance. `run.json`, `details` and the split log record each model with its source (`modelSource`, `workerModels`); `/orche models` shows the three tiers and their sources. Main's hand-off rule names the configured orchestrator model only when `models.orchestrator` is set.

- **Split log** (`docs/orchestrator.md` 11): every finished orche_task assignment appends one short JSON line (time, role, orchestrator or not, split decision and criteria, sub-workers, requests, duration, provider-reported cost, status, model, record path; no request text) to `split-log.jsonl` in the records root, which record pruning does not touch; it rotates once at 2 MB. `/orche splits [days]` shows the split rate, the criteria and cost/time by decision over all sessions. Usage events now carry the provider-reported cost.

- **Single-workflow orchestrator** (`single.spawn`, default on; `docs/orchestrator.md`, `src/orchestrator/`). The implement/answer worker of the single workflow is the task's orchestrator: before it works it decides whether the task needs splitting by three criteria (Parallelism, Isolation, Independent verification), does not split by default, and reports the decision in `data.split` (`Split:` line, `details.split`). When a criterion clearly holds it calls the new worker-only tool **`orche_spawn`** (`{reason, workers:[{name, role, request, files}]}`): up to 4 sub-workers in fresh one-shot sessions at the same time. Sub-workers see only their own request, cannot spawn (depth 1), inherit the orchestrator's model and thinking (game-asset/video keep their routes), may write only their own files (overlapping ownership refuses the call; writes into a sibling's or unowned files are blocked; a workspace diff around the call warns about the rest); a `verification` call starts fresh read-only verifiers only. Results list the sub-workers (`details.spawned`), records add them as agents with a `spawn` event. The split instruction was chosen by a pre-registered one-turn evaluation (`experiments/judgment/`, 45 labelled tasks × 4 instruction variants × 2 models): the checklist variant scored 98.9% with 0% unnecessary splits on claude-opus-5-5 and 97.8% / 0% on gpt-6.1-sol, while the three questions alone split 24% / 56% of the tasks that should not be split. A third pre-registered evaluation on 87 requests sampled from recorded real sessions (`experiments/judgment/real/`: deterministic extraction, filtering and labels from the recorded work; request text stays out of the repository) kept the checklist again: 95.5% correct with 2.0% unnecessary splits and no unnecessary parallel split on claude-opus-5-5. End-to-end smoke (8 runs, all passing hidden tests): no split on a coupled migration, a fresh verifier when the user asked for independent review, no split on four small independent tickets (same wall time, 1.6–1.8× cost when split on request), four parallel sub-workers when the user asked for them. A second pre-registered evaluation (`experiments/judgment/` v2: labels by measured work size, a new fixture `fixtures/parallel/p4-stdlib-ports`, 22 fixture tasks judged after reading the repository through the product prompt, 2 models × 3 variants × 2) kept the checklist; end to end on p4 the orchestrator did not split, and a split run finished 11% sooner at 1.6× the cost. The orchestrator's assignment and system prompt no longer say "You work alone" (gpt-6.1-sol cited it to refuse valid splits; corrected: 0% missed parallel). `"single": { "spawn": false }` keeps the earlier single worker exactly. Main's single rules add one paragraph (the worker decides about splitting; main puts the user's explicit review wishes into the request).

- `orche_task` takes `gui: true` for a worker with its own private GUI desktop, provided by the pi-gui package through a generic worker-capability contract (`pi.events` channel `orche:worker-capability`; `WorkerCapabilityProvider`). The provider's extension factories load into that worker's session only and their tools join its allowlist; the session is bound (`session_start`) and its disposal emits `session_shutdown`, so the capability's resources (pi-gui: one computer-use-mcp process and private desktop per worker) stop with the worker. Omitted keeps a reused worker's setting; changing it starts a fresh worker. Without a provider the task fails before any worker is touched. `createSession` gained `extensionFactories` for this.

- Opt-in single-workflow task ledger (`"single": { "ledger": true }` in `orche.config.json`, default off): per task, the original requests, each assignment's requirements with the last reported status, the readings chosen for ambiguous requirements and a short history, kept outside LLM contexts as small `orche-ledger` event entries (one per hand-off, result or failure; restored by replay). `orche_task` takes `task` (the `T…` id named in results) to continue a task, also with another or a new worker; without it every assignment starts a new task, even on a reused worker. Workers get the task's ledger back when they compact, the main session gets a summary after its own compaction, and a task whose worker is gone continues with a new worker briefed from the ledger (`details.task`, `details.continuedFrom`). Phase 1 of `docs/specialist-orchestration.md`.

### Removed

- **The multi-worker coordinator and everything only it used (BREAKING, 0.2.0)**: `OrcheController.run()` and the coordinator (`src/orchestration/coordinator.ts`, `run/{answer,change,decisions,diagnose,context,audit,root-ownership,types}.ts`, `phases.ts`, `team.ts`, `artifacts.ts`, `events.ts`), the advisors (`src/advisor/`), the standalone CLI (`src/cli.ts`), the unregistered `code_nav` tool, the benchmark runners of `src/eval/` (only `suite.ts`, used by `scripts/validate-suite.ts` and `experiments/workflow/driver.ts`, stays) and their tests. The extension had not registered `orche_run` since auto/multi were removed; nothing it loads used this code (files reachable from `src/extension/index.ts`: 78 before, 60 after, none added). Tests no longer import the gitignored `results/advisor-study/`, so a fresh clone type-checks and tests clean. Configs that still set `advisors`, `audit`, `workers.maxWorkers` or `workers.answerAngles` load; the keys are ignored with a warning (`workers.explorerRoles` still picks the explore worker's route).

- **Single pipeline v2, the workflow policies and `single.mainReview` were removed** (`docs/orchestrator.md` 4): the Framer, the risk-gated Verifier with fix rounds and probe rechecks, `code_nav` registration, the investigation critic, creation divergence, `orche_task`'s `type`/`candidates`/`then` and the `evidence` main review. None had passed a benchmark gate (v2: 22/24 vs 23/24 at 1.83× cost per success; critic/divergence never measured), and the orchestrator covers independent verification on request. Configs that still set `single.pipeline`, `frame`, `checker`, `nav`, `mainReview`, `investigation` or `creation` load; the keys are ignored with a warning at session start. The risk score moved to `experiments/risk/`; `experiments/workflow/` and the investigation/creation fixtures stay as experiment material.

- **The `auto` and `multi` main modes, the `orche_run` tool and `/orche multi` were removed from the Pi package.** Benchmarks (bench3, hard6, parallel3, multi-vs-single) showed the multi-agent orchestrator no more accurate than one worker on coupled or parallel tasks at about twice the cost. The package now offers `direct` (default) and `single`; a config value or saved session choice of `auto`/`multi` is read as `single` with a warning, and `/orche mode auto|multi` is a usage error. The failed-run handover to `orche_task` and the four-file "consider orche_run" note are gone. The orchestration engine (`runOrchestrated`, the CLI, eval arms) stays as a library; the eval `pi-orche` arm now uses `mainMode: single`.

### Changed

- **Queued follow-ups no longer detach an attached `orche_task`/`orche_task_attach`** (README "Background tasks", docs/tools.md "Follow-ups"): a follow-up (Alt+Enter, RPC `follow_up`) stays in Pi's queue and is delivered after the job's result, as for any other tool call; it no longer makes main end its turn. Only steered input, woken pi-session-bus notes, Esc and `/orche detach` detach. The attach guard refuses only for a waiting steer or note, so queued follow-ups no longer make `orche_task_attach` return at once; steers queued together with follow-ups are still answered first. The `followUp` detach reason is gone (older sessions still render it).
- **Pi 1.1.0 and host `typebox`**: the `@earendil-works/*` dev dependencies are 1.1.0 and the package imports `typebox` (1.3.27, the version Pi supplies) instead of `@sinclair/typebox` 0.34, which Pi only aliased at runtime: `peerDependencies` names `typebox` as Pi's `docs/packages.md` asks, and tests and type checks now run on the TypeBox generation Pi loads. The `orche_spawn` reason/role unions keep their JSON Schema and are typed as tuples for TypeBox 1.x `Static`.
- **`read` gives codemode scripts structured results** (`src/tools/read.ts`): it declares Pi's read `outputSchema` and returns `structuredContent`, so `tools.read()` in a codemode script resolves to the image block `{ type, data, mimeType, note }` for images and to the same anchored text the model sees for text, outline and symbol reads. Model-facing content, details and anchor history are unchanged.
- **Docs follow the current structure**: the README opens with the Pi package (single: main → orchestrator → sub-workers only when needed; direct), recommends `/orche direct <PROMPT>` for light requests, and drops the coordinator, CLI, `runOrchestrated` and advisor sections; `docs/pi-package.md` no longer lists `auto`/`multi` in `/orche` usage and documents `/orche splits`. Design and experiment documents of removed features (specialist-orchestration, workflow-policy, dag-orchestration, bench3, advisor, advisor-study, comparison, evaluation, prompt-study) start with a "역사 기록" status line pointing to `docs/orchestrator.md`; their bodies are unchanged.

- **Single mode: main now reviews a worker's result from its report**: it reads the checklist, the checks the worker names and the readings it chose, and checks the readings against the user's wording, but no longer re-reads the changed code or re-runs the project checks itself. That re-verification was all of main's tool use after results and most of its context. Pre-registered benchmarks G-M and G-M2 (6 long sessions of 8 tasks per arm, pooled): 48/48 tasks against 46/48, main context max 0.41×, cost 0.97× (0.93× per passed task). (It was first a `single.mainReview` setting with an `evidence` fallback; the setting was removed with the orchestrator redesign.)
- Single mode: main classifies every user message by work type before acting (`src/single/work-types.ts`): **respond** (only restate or reformat its previous reply; answered without a task), **investigation** (information only; role `answer`), **execution** (a requested or authorized change, an approval of a proposal, or a bare bug report, which is diagnosed and fixed; role `implement`), **creation** (open-ended creative artifacts; `game-asset`/`video` or `implement`). In an offline evaluation of 123 labelled requests these definitions routed 94–97% correctly with high-end models, against 88% for a TypeSafe Jev classifier with rules (`experiments/routing/`, which evaluates any classifier or chat model).

- **Default `mainMode` is `single`** (one reusable `orche_task` worker per task); `direct` (the main edits with its own tools) is chosen with `/orche mode direct` or `mainMode: "direct"`. An unset or invalid `mainMode` means `single`. (An interim change had made `direct` the default after benchmarks (bench3, hard6, parallel3, long sessions) showed single agents matching delegated quality at lower cost and latency; it was reverted.)
- Direct mode warns the user once when the main session's context crosses 50% and 75% of the window, suggesting `/orche mode single` (a worker carries the context) or `/compact`; re-arms after usage drops 10 points below the lowest threshold. Configurable via `contextWarning: { enabled, thresholds }`.
- Single-workflow checklists are treated as worker self-reports: implement items reported `met` must name the passing check in `verifiedBy` (otherwise report `partial`), workers report alternative readings of ambiguous requirements in `data.ambiguities`, and results show `met` vs named-check counts plus a review note for ambiguities. Main checks each reported reading against the user's original wording and reports unverified items as unverified. (An interim rule also told main to confirm that each cited `verifiedBy` check asserts the acceptance; it was dropped because main then read the tests itself: its context peak in an 8-task session rose from about 76K to 123K tokens with no better pass rate.)
- Added opt-in `PI_ORCHE_TOOL_EVENTS` metadata-only JSONL for output reductions and artifact accesses, with original-line visibility ranges and session ids, without changing tool output.
- Redesigned the single workflow (single mode and auto's `orche_task` path): intent/purpose and testable R-id requirements with the original user request verbatim; worker-owned sequential Task DAG via worker-only `task_plan`; required implement/answer checklists, same-worker evidence review and new-worker hand-off of only items unmet/partial for two consecutive assignments.
- Single-workflow task standard roles inherit main's current model/thinking at each hand-off, including extended context; unavailable models warn and fall back to routing, and reused-worker switch failures suggest a fresh worker. Specialists and multi runs retain routing. Task sessions compact above 50%, synchronously restoring the hand-off and latest plan; compaction resets projection indices until the next assignment boundary and replaces 70% retirement. Plans, checklists, effective model/effort and compaction count/token estimates are recorded.
- Auto chooses multi only for an explicit multi-agent/parallel-worker request, clearly parallel substantial independent units with disjoint write sets, or clearly warranted competing hypotheses for an unknown defect cause. Ambiguous requests use single; size/risk/verification/failure alone no longer trigger multi. Multi/direct rule text and failed-run handover remain unchanged.
- Failed, non-cancelled extension `orche_run` calls in auto mode now hand live workers and their full contexts to `orche_task`, with collision-free usable ids, roles, last tasks and remaining issues in the result. Auto delegation recovers via those workers rather than repeating the run; multi mode reports skipped handover. Successful/cancelled runs and SDK callers without the opt-in hook retain normal disposal.
- One-worker `change` runs now need only the classification coordinator decision: deterministic repository-wide execution, V1 verification, context-preserving fixes within the normal cap, and a composed implementation/verification summary. Blocked implementers and exhausted verification fail without coordinator replanning; larger changes and other classes are unchanged.
