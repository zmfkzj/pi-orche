# Changelog

## [Unreleased]

### Added

- **Single-workflow orchestrator** (`single.spawn`, default on; `docs/orchestrator.md`, `src/orchestrator/`). The implement/answer worker of the single workflow is the task's orchestrator: before it works it decides whether the task needs splitting by three criteria (Parallelism, Isolation, Independent verification), does not split by default, and reports the decision in `data.split` (`Split:` line, `details.split`). When a criterion clearly holds it calls the new worker-only tool **`orche_spawn`** (`{reason, workers:[{name, role, request, files}]}`): up to 4 sub-workers in fresh one-shot sessions at the same time. Sub-workers see only their own request, cannot spawn (depth 1), inherit the orchestrator's model and thinking (game-asset/video keep their routes), may write only their own files (overlapping ownership refuses the call; writes into a sibling's or unowned files are blocked; a workspace diff around the call warns about the rest); a `verification` call starts fresh read-only verifiers only. Results list the sub-workers (`details.spawned`), records add them as agents with a `spawn` event. The split instruction was chosen by a pre-registered one-turn evaluation (`experiments/judgment/`, 45 labelled tasks × 4 instruction variants × 2 models): the checklist variant scored 98.9% with 0% unnecessary splits on claude-opus-5-5 and 97.8% / 0% on gpt-6.1-sol, while the three questions alone split 24% / 56% of the tasks that should not be split. End-to-end smoke (8 runs, all passing hidden tests): no split on a coupled migration, a fresh verifier when the user asked for independent review, no split on four small independent tickets (same wall time, 1.6–1.8× cost when split on request), four parallel sub-workers when the user asked for them. A second pre-registered evaluation (`experiments/judgment/` v2: labels by measured work size, a new fixture `fixtures/parallel/p4-stdlib-ports`, 22 fixture tasks judged after reading the repository through the product prompt, 2 models × 3 variants × 2) kept the checklist; end to end on p4 the orchestrator did not split, and a split run finished 11% sooner at 1.6× the cost. The orchestrator's assignment and system prompt no longer say "You work alone" (gpt-6.1-sol cited it to refuse valid splits; corrected: 0% missed parallel). `"single": { "spawn": false }` keeps the earlier single worker exactly. Main's single rules add one paragraph (the worker decides about splitting; main puts the user's explicit review wishes into the request).

- Opt-in single-workflow task ledger (`"single": { "ledger": true }` in `orche.config.json`, default off): per task, the original requests, each assignment's requirements with the last reported status, the readings chosen for ambiguous requirements and a short history, kept outside LLM contexts as small `orche-ledger` event entries (one per hand-off, result or failure; restored by replay). `orche_task` takes `task` (the `T…` id named in results) to continue a task, also with another or a new worker; without it every assignment starts a new task, even on a reused worker. Workers get the task's ledger back when they compact, the main session gets a summary after its own compaction, and a task whose worker is gone continues with a new worker briefed from the ledger (`details.task`, `details.continuedFrom`). Phase 1 of `docs/specialist-orchestration.md`.

### Removed

- **Single pipeline v2, the workflow policies and `single.mainReview` were removed** (`docs/orchestrator.md` 4): the Framer, the risk-gated Verifier with fix rounds and probe rechecks, `code_nav` registration, the investigation critic, creation divergence, `orche_task`'s `type`/`candidates`/`then` and the `evidence` main review. None had passed a benchmark gate (v2: 22/24 vs 23/24 at 1.83× cost per success; critic/divergence never measured), and the orchestrator covers independent verification on request. Configs that still set `single.pipeline`, `frame`, `checker`, `nav`, `mainReview`, `investigation` or `creation` load; the keys are ignored with a warning at session start. The risk score moved to `experiments/risk/`; `experiments/workflow/` and the investigation/creation fixtures stay as experiment material.

- **The `auto` and `multi` main modes, the `orche_run` tool and `/orche multi` were removed from the Pi package.** Benchmarks (bench3, hard6, parallel3, multi-vs-single) showed the multi-agent orchestrator no more accurate than one worker on coupled or parallel tasks at about twice the cost. The package now offers `direct` (default) and `single`; a config value or saved session choice of `auto`/`multi` is read as `single` with a warning, and `/orche mode auto|multi` is a usage error. The failed-run handover to `orche_task` and the four-file "consider orche_run" note are gone. The orchestration engine (`runOrchestrated`, the CLI, eval arms) stays as a library; the eval `pi-orche` arm now uses `mainMode: single`.

### Changed

- **Single mode: main now reviews a worker's result from its report**: it reads the checklist, the checks the worker names and the readings it chose, and checks the readings against the user's wording, but no longer re-reads the changed code or re-runs the project checks itself. That re-verification was all of main's tool use after results and most of its context. Pre-registered benchmarks G-M and G-M2 (6 long sessions of 8 tasks per arm, pooled): 48/48 tasks against 46/48, main context max 0.41×, cost 0.97× (0.93× per passed task). (It was first a `single.mainReview` setting with an `evidence` fallback; the setting was removed with the orchestrator redesign.)
- Single mode: main classifies every user message by work type before acting (`src/single/work-types.ts`): **respond** (only restate or reformat its previous reply; answered without a task), **investigation** (information only; role `answer`), **execution** (a requested or authorized change, an approval of a proposal, or a bare bug report, which is diagnosed and fixed; role `implement`), **creation** (open-ended creative artifacts; `game-asset`/`video` or `implement`). In an offline evaluation of 123 labelled requests these definitions routed 94–97% correctly with high-end models, against 88% for a TypeSafe Jev classifier with rules (`experiments/routing/`, which evaluates any classifier or chat model).

- **Default `mainMode` is `single`** (one reusable `orche_task` worker per task); `direct` (the main edits with its own tools) is chosen with `/orche mode direct` or `mainMode: "direct"`. An unset or invalid `mainMode` means `single`. (An interim change had made `direct` the default after benchmarks (bench3, hard6, parallel3, long sessions) showed single agents matching delegated quality at lower cost and latency; it was reverted.)
- Direct mode warns the user once when the main session's context crosses 50% and 75% of the window, suggesting `/orche mode single` (a worker carries the context) or `/compact`; re-arms after usage drops 10 points below the lowest threshold. Configurable via `contextWarning: { enabled, thresholds }`.
- Single-workflow checklists are treated as worker self-reports: implement items reported `met` must name the passing check in `verifiedBy` (otherwise report `partial`), workers report alternative readings of ambiguous requirements in `data.ambiguities`, and results show `met` vs named-check counts plus a review note for ambiguities. Main checks each reported reading against the user's original wording and reports unverified items as unverified. (An interim rule also told main to confirm that each cited `verifiedBy` check asserts the acceptance; it was dropped because main then read the tests itself: its context peak in an 8-task session rose from about 76K to 123K tokens with no better pass rate.)
- Added opt-in `PI_ORCHE_TOOL_EVENTS` metadata-only JSONL for output reductions and artifact accesses, with original-line visibility ranges and session ids, without changing tool output.
- Redesigned the single workflow (single mode and auto's `orche_task` path): intent/purpose and testable R-id requirements with the original user request verbatim; worker-owned sequential Task DAG via worker-only `task_plan`; required implement/answer checklists, same-worker evidence review and new-worker hand-off of only items unmet/partial for two consecutive assignments.
- Single-workflow task standard roles inherit main's current model/thinking at each hand-off, including extended context; unavailable models warn and fall back to routing, and reused-worker switch failures suggest a fresh worker. Specialists and multi runs retain routing. Task sessions compact above 50%, synchronously restoring the hand-off and latest plan; compaction resets projection indices until the next assignment boundary and replaces 70% retirement. Plans, checklists, effective model/effort and compaction count/token estimates are recorded.
- Auto chooses multi only for an explicit multi-agent/parallel-worker request, clearly parallel substantial independent units with disjoint write sets, or clearly warranted competing hypotheses for an unknown defect cause. Ambiguous requests use single; size/risk/verification/failure alone no longer trigger multi. Multi/direct rule text and failed-run handover remain unchanged.
- Failed, non-cancelled extension `orche_run` calls in auto mode now hand live workers and their full contexts to `orche_task`, with collision-free usable ids, roles, last tasks and remaining issues in the result. Auto delegation recovers via those workers rather than repeating the run; multi mode reports skipped handover. Successful/cancelled runs and SDK callers without the opt-in hook retain normal disposal.
- One-worker `change` runs now need only the classification coordinator decision: deterministic repository-wide execution, V1 verification, context-preserving fixes within the normal cap, and a composed implementation/verification summary. Blocked implementers and exhausted verification fail without coordinator replanning; larger changes and other classes are unchanged.

- Reused `orche_task` workers bound earlier tool output with a cache-stable, restorable assignment-boundary projection that changes only with new clears. Affected earlier reasoning is cumulatively omitted for signature safety, and paired Responses item IDs are dropped without breaking call/result pairing; raw records stay complete. Validated `taskContext` settings and clearing counts are in results/record events. `clearBetweenAssignments: false` means no new clears: existing projections remain unchanged until compaction resets them; never-cleared workers remain unprojected. Other sessions do not project context, but shared validation means invalid `taskContext` also fails `orche_run`.
- Reduced read anchors to four hex characters, omitted blank-line tags, and kept 4–16-hex backward compatibility; earlier-read anchors rebase across the tool's own edits, rejecting ambiguous surviving targets. Current read/symbol anchors always win, so re-reading resolves ambiguity.
- Compacted edit echoes to one-line context / 40 lines with long-operation collapse, and added non-blocking JS/TS parse-error feedback.
- Added JS/TS/Markdown read outlines and named-symbol reads with normal edit anchors; `outline: false` is unset and blank symbols are rejected.
- Filtered bash test/compiler/linter noise and grouped repeated grep paths, preserving diagnostics and recoverable full-output artifacts; analysis clips lines at 2,000 characters, scans their full tails for diagnostic words and reports the clip count, and skips specialized filters above 2 MB. Over-threshold specialized summaries fall back to bounded original-output previews, prioritizing middle errors over warnings and counting omitted diagnostics.
- Delegation now passes references rather than copied files/logs, and worker reports are conclusion-first with location evidence. Run worker instructions are static per role/loadout, with identity/request/language briefed in the first assignment for cache reuse.
- Rebuilt eval summaries now record the artifact directory actually read, so relocated study directories remain analysable.

### Fixed

- Single-workflow review fixes: historical/superseded compaction essentials and explicit reused-assignment precedence; assignment-local plan reset, bounded DAG validation (1–60 nodes, title ≤200, note ≤500, 64 KiB payload, one running node), request-local coverage validation/warnings and a visible missing-plan note without rejecting reports.
- Checklist ids now come only from requirement declaration lines outside case-insensitive original-request header variants; incidental prose/path ids do not require a checklist. Answer rejection hints use the registered answer schema. Unmet streaks are per worker and reset on met/omitted/renamed/revised requirements or failed assignments.
- Task DAG tools and 50% auto-compaction now apply only to standard single-workflow roles, not game-asset/video specialists. An absent main model warns and keeps a reused worker's current model/thinking, or uses routes on spawn. Auto's prose defaults changes to single without phase splitting or stopping for size/risk; single-workflow results no longer add a four-file size note, while blocked/failed-verification notes keep concrete same-worker reasons.

- Single main mode refines requirements and delegates the whole task in one end-to-end `orche_task` assignment (`implement` for changes, `answer` for read-only questions), without phase splitting or asking for a mode switch. The worker investigates, implements, tests and iterates; main accepts with trusted checks and sends problems/follow-ups to the same worker. Separate verification is only on explicit user request; auto now shares this task workflow (see above).
- Directory `ast_rewrite` now checks ownership per matching file at write time, skipping and listing blocked files instead of failing the whole call. Directory rewrites never follow file symlinks or escape their target directory, and guarded sessions without a per-file guard fail closed.
- Multi-run workspace audits now include uncommitted submodule files and moved submodule HEADs. Worker-attributed HEAD moves still undergo ownership checks and retain submodule-aware checkout recovery; quiet external moves are not restored.
- Disposed workers release their sessions and adapters instead of retaining full transcripts; lightweight status and record data remain available.
- Worker startup observes cancellation and assignment deadlines. An unresponsive SDK abort is bounded to one second by default, then the worker is force-disposed so subsequent tasks can start.
- Each assignment uses its freshly resolved `limits.assignmentRequests` budget, including changes between tasks on a reused worker.
